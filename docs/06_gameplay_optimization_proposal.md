## 2. 未记录的实际玩法差异

按影响从大到小排序。

### B1 · 存储型机柜的「抗波动」特性未实现 ⚠️ 最重要

- **设计**（01§5）：存储型 =「玉米：便宜、低耗低热、收益低但**几乎不受行情波动影响**」。
- **实现**（`game_rules.gd:datacenter_income_per_month`）：行情倍率 `market_multiplier(customer_id)` 统一乘在整座机房上，存储柜与 GPU 柜随行情**满幅同步波动**。
- **后果**：三机型的「稳 / 平衡 / 暴利」三角只剩二角。时代 1 存储柜被计算柜严格支配（互联网客户下 $/成本效率 0.175 vs 0.36，$/耗电 35 vs 54），要到时代 2 云厂商混插加成才有存在意义——「种什么菜」的开局选择实际是伪选择。

### B2 · 网络 L3/L4 与时代 3 的「大单事件」缺失

- **设计**（02§4.4）：L3 专线解锁「云厂商大单事件」，L4 骨干节点解锁「AI 专属大合约事件」；01§7 时代 3 也承诺「AI 专属大合约事件」。
- **实现**：`MarketSystem._pick_event` 只按 `minimum_era` 过滤，事件 schema 没有网络等级字段；事件池 12 条里没有任何大单类事件。L3（$60k）/L4（$400k）退化为纯收入乘数 ×1.35 / ×1.6。
- **后果**：中后期最贵的两笔全局投资只是「数字大一点」，没有设计里「解锁新内容」的目标感；时代 3 的新增内容也偏薄（只有 T3 机房、GPU T2、液冷 T2、一条算力过剩负面事件）。

### B3 · 合约期没有成为节奏锚点

- **设计**（01§6.1）：合约期 6 游戏月，「到期自动续约、可随时毁约换客户（付小额违约金），引导看行情调结构」。
- **实现**：到期在 `_process_contract_renewals` 中**静默**滚动续约；毁约费任意时刻恒定为月收入 10%（最低 $25）。
- **后果**：合约到期这个时间点对玩家不可见、无任何决策或奖励；由于毁约费远低于行情事件的收益差（如挖矿 ×2.5 或 ×0.2），最优策略是无视合约随时追涨——「合约以机房为单位」只剩下选择乘数的意义。

### B4 · 机柜上架占用全局建设队列

- **设计**（01§5）：上架是每台机柜自己的「分钟级计时器」；建设队列（01§2 中循环）指机房/供电/冷却。
- **实现**：`install_rack` 走 `construction_queue`，与建机房、附件、网络升级共享容量 2。
- **后果**：中期填一座 9 柜 T2 机房需要 9 次排队，与扩张动作互相阻塞；「买了机器等着装」的摩擦不产生任何决策价值。

### B5 · 小项（列出备查）

1. **供电分配隐式**：容量不足时按槽位序号贪心供电（slot 0 优先），设计未定义、UI 未解释，玩家无法指定哪台机柜优先。
2. **故障率采样滞后**：λ 只在排定下次故障时读取过热/老化状态；机柜后来才过热的（如邻柜上架挤占冷却预算）不会即时加速故障。附件变更和老化阶段切换会重排，但上架/下架机柜不会。
3. **激进型未触发欠费**：30 天固定种子模拟最低现金 $24 但欠费 0 次（`balance_report.md` 已自陈）；「破产是真实威胁」目前只在理论上成立。
4. **转生节奏未验证**：设计预期第 2~3 周首次转生（累计建成 ≥ 20 座）；模拟报告只输出了 30 日存量机房数（活跃型 16 座），没有输出 `total_datacenters_built`（含退役），无法确认是否达标。

## 3. 优化方案

原则：优先补齐设计已承诺但缺失的内容（P0）；其次是低成本高回报的决策深度增强（P1）；纯数值验证类放 P2。所有改动优先落在 `data/*.json`，代码改动标注涉及文件。**任何数值改动都必须重跑 `tools/simulate_economy.py` 并存档曲线（02§10 铁律）。**

### P0-1 · 机型行情敏感度（修复 B1）

给机柜类型加 `market_sensitivity` 字段，实际行情倍率按敏感度插值：

```
有效倍率(kind) = 1 + (行情倍率 - 1) × sensitivity(kind)
建议首版：storage 0.3 / compute 1.0 / gpu 1.2
```

- 存储找回「稳」的身份：行业寒冬 ×0.75 时存储只跌到 ×0.925，成为防御性资产；GPU 波动进一步放大，强化「暴利/跳水」。
- 顺带微调 `customers.json` 中互联网对存储的 fit 0.7 → 0.85，让时代 1 的存储不再被严格支配（保持低于计算，仍是「慢」）。
- 改动面：`data/racks.json` 加字段；`game_rules.gd:datacenter_income_per_month` 把倍率乘法移进逐柜循环（约 5 行）；模拟器同步。
- 风险：云厂商混插加成的价值会略升（存储更稳），需模拟器确认「无单一最优柜型」验收项仍成立。

### P0-2 · 大单合约事件（修复 B2）

不加新系统，扩展现有事件 schema 实现设计承诺：

1. `events.json` 事件项支持 `minimum_network_level` 字段；`MarketSystem._pick_event` 增加一行过滤。
2. 新增 3~4 条「大单」事件（高倍率、定向、稀有）：

| 事件（示意） | 影响 | 持续 | 权重 | 门槛 |
|---|---|---|---|---|
| 云厂商年度框架大单 | 云厂商 ×2.2 | 4 月 | 3 | 时代 2 + 网络 L3 |
| 主权 AI 训练合同 | GPU 厂商 ×3.5 | 3 月 | 3 | 时代 3 + 网络 L4 |
| 海外节点招标 | 互联网 ×2.0 | 2 月 | 3 | 网络 L3 |
| AI 推理需求爆发 | GPU 厂商 ×2.0、云厂商 ×1.3 | 3 月 | 4 | 时代 3 |

- L3/L4 的购买理由从「+20% 乘数」变成「解锁只有你能吃到的大行情」；时代 3 内容同时得到补强。
- 改动面：`data/events.json`、`market_system.gd`（1 行过滤）、本地化 8 条文案。
- 注意：大单事件进入池子会稀释现有事件权重，倍率上限 ×3.5 需模拟器验证不破坏中期曲线。

### P0-3 · 合约续约窗口（修复 B3）

- 合约到期后 **1 游戏月（2 现实小时）内换客户免毁约费**；窗口内不换则自动续约（行为与现状一致，只是把静默续约推迟到窗口结束）。
- 到期时发一条 EventBus 通知（离线大事记同样列出），把「合约到期」变成一个可运营的回访钩子。
- 配合调平：提前毁约费 `breach_fee_monthly_income_ratio` 0.1 → 0.25（「提前毁约贵、到期换免费」，追涨需要权衡剩余合约期）。
- 改动面：`data/economy.json` 加 `renewal_window_seconds` 与新费率；`game.gd` 的 `sign_contract` / `contract_switch_fee` / `_process_contract_renewals` 小改；UI 层提醒交给 UI session 排期。

### P1-1 · 机柜上架脱离全局队列（修复 B4）

- 上架/替换机柜不再占 `construction_queue`，改为机柜自身的 `install_complete_at` 计时（数据结构里已有 `status: installing`，顺势即可）；每座机房同时在装数量上限 2，防一键铺满。
- 机房、供电、冷却、网络仍走全局队列（这是设计里的中循环等待，保留）。
- 改动面：`game.gd:install_rack` / `_complete_rack` / `_next_boundary_after`；存档 shape 兼容（`_ensure_state_shape`）。
- 广告/钻石加速入口对机柜保持可用，商业化位不减少。

### P1-2 · 供电管理显性化（修复 B5-1）

- 第一步（零代码风险）：规则文档化 +「编号小的槽位优先供电」写进 UI 文案，交 UI session。
- 第二步（建议）：机柜增加「停机」开关（手动下电，不产出、不故障、不耗容量）。这让「容量不足时保谁」成为玩家决策，也是后续「行情差时给 GPU 柜停机省故障费」的微策略来源。
- 改动面：`game.gd` 新增 `set_rack_enabled`；`game_rules.gd:powered_slots` 跳过停机柜（约 10 行）。

### P1-3 · 过热即时重排故障（修复 B5-2）

- `install_rack` 完成与 `uninstall_rack` 时对该机房调用现成的 `_reschedule_dc_faults`。两行改动，让过热惩罚即时生效。

### P1-4 · 中期维护压力（修复 B5-3）

激进型应当在第 5~10 天经历欠费惊魂（02§10 验收项），当前未达成。两个选项：

- **选项 A（纯数值，推荐先试）**：T2 维护 900 → 1150、T3 5000 → 6200，多种子重跑，目标激进型欠费率 30%~60%、破产率 < 10%，且不拖垮挂机型曲线。
- **选项 B（需所有者拍板 ⚠️）**：新增负面事件「电价上涨：全体机房维护费 ×1.5，持续 2 月」。机制上只是事件乘数，但「电价」字面与锁定的「不做电价峰谷/负载调度」相邻——若采用建议改名为「运营成本上升」，并在 00_decisions 补一条记录。

### P2 · 验证与调平项（不改机制）

1. **转生节奏**：模拟器输出 `total_datacenters_built`（含退役），验证活跃型能否在第 14~21 天达到 20 座；达不到则把门槛 20 → 15，或教学集装箱计入，二选一报所有者。
2. **P0/P1 全量回归**：重跑三策略 × 多种子，沿用 02§10 验收，并新增两条：活跃型第 14~21 天完成首次转生；每类客户在活跃型 30 天内的签约时长占比均 ≥ 10%（验证四类客户都有出场机会，大单事件没有把生态压成单一客户）。
3. 曲线截图照旧存 `docs/balance_runs/`，结论回写 `balance_report.md`。

## 4. 明确不建议做的

- 不加 PUE、电价调度、冗余设备、拓扑等锁定排除项（00_decisions「明确不做」）。
- 不给冷却系统加新机制（如相邻加热）：轻邻接的价值就是简单，GPU T2 发热 9 在现有数值下已需要液冷或双风冷 T2 交叉覆盖，深度够用。
- P02 钻石重组自救维持默认关闭，等测试期数据。
- 不动时间换算、老化曲线、转生公式本体——模拟器已验证的骨架不为提案翻新。

## 5. 建议实施顺序

```
P0-1 机型行情敏感度 ──┐
P0-2 大单合约事件   ──┼─→ 一次模拟器回归（多种子）─→ P1-1 上架脱队列 ─→ P1-2/3 小改 ─→ P1-4 压力调平 ─→ P2 验证
P0-3 续约窗口       ──┘
```

P0 三项互相独立但共享一次调平回归，适合作为同一个改动批次；P1-1 涉及存档 shape，单独批次并加迁移测试。全部改动完成后按 README 验收命令走一遍门禁。
